# The KronosDB native protocol

Version 2. One long-lived TCP connection per client, with optional TLS,
carrying multiplexed request streams of little-endian, fixed-layout frames,
each stream paced by its own window.

Every byte on the wire is declared in [`kronosdb.schema`](kronosdb.schema).
The codecs, the message reference at the end of this document, and the golden
fixtures are generated from it; nothing here is maintained by hand twice.

## Conformance

A client is conformant when it passes the golden fixtures: for every
`fixtures/NAME.bin`, decoding the frame yields exactly `fixtures/NAME.json`,
and encoding that value yields exactly the `.bin` bytes. The fixtures are
produced by a reference codec in the generator that interprets the schema
directly and shares no code with the generated codecs, so an emitter bug
cannot hide behind a matching fixture.

The JSON form maps `u8`, `u16`, `u32` and `millis` to numbers, `u64` and
`i64` to decimal strings, bytes to lowercase hex, an absent `opt` to `null`,
enums to their variant name (or the number, for a value the schema does not
know), a union to an object with one key naming the variant, and a record
to `{"flags", "event"}`.

A new implementation — another language, or a hand-tuned hot path — must run
the same fixtures. Generated files carry the schema's `SCHEMA_HASH`, so a
client repository can check it is built against the version it claims.

## Connection

A client opens a TCP connection, sends the 8-byte preface `KRONOSDB`, and then
its [Hello](#hello). A server configured with TLS expects the TLS handshake
first, on the same port, and has no plaintext fallback. The server answers with
[Welcome](#welcome), or with [RequestFailed](#requestfailed) on stream 0 and
closes the connection.

Hello carries the credentials. The server resolves `token` and `jwt` alike —
a static token first, then a JWT from a trusted issuer — so a client that
cannot tell which it holds sends `token`. With TLS client certificates the
certificate identifies the client instead, and Hello's credential kind is
`none`. The
principal the server resolves is fixed for the connection until a
[Reauthenticate](#reauthenticate) replaces it, which a client sends before its
token expires. Authorization happens per request, against that principal.

Either side may close the connection at any time. A server about to shut down
sends [GoAway](#goaway) first: it accepts no new streams after it, finishes
the open ones, then closes.

### Liveness

The server sends [ServerPing](#serverping) on a connection that has been idle
for Welcome's `heartbeat` milliseconds, and closes it after two missed
[ClientPong](#clientpong)s. A client may check the server the same way with
[Ping](#ping) and [Pong](#pong).

## Frames

```
len u32 | kind u16 | flags u8 | stream u32 | body
```

`len` counts every byte after itself, so a frame is `4 + len` bytes. A frame
larger than Welcome's `max_frame` is a protocol violation. Welcome reports the
limit that applies to the connection: a server may allow a verified peer, which
replicates log segments in frames of tens of megabytes, more than a client.
The body is the frame's fields in schema order.

`kind` names the frame. Kinds with the `0x8000` bit are sent by the server,
the rest by the client. A frame of the wrong direction is a protocol
violation.

`flags` bit 0 is `END`: the sender will send nothing more on this stream. The
other bits are reserved and must be 0.

### Streams

`stream` multiplexes requests. Stream 0 is the connection itself: Hello,
Welcome, the pings and GoAway, and nothing else. Every other stream is opened by the client
with a request frame on any id not currently in use, and is finished once
both sides have sent `END` — or once the server sends RequestFailed, which
always ends the stream. The client may reuse an id after its stream finished.

Requests take one of three shapes:

- **Unary** (Append, GetHead, …): the request carries `END`; the server
  answers with exactly one frame, which carries `END`.
- **Server stream** (Source, SnapshottedSource, Subscribe, DispatchQuery):
  the request carries `END`; the server answers with frames until one carries
  `END`. A subscription has no last frame of its own: it runs until the
  client cancels it.
- **Two-way stream** (the handler streams, OpenPlatform,
  OpenSubscriptionQuery, TailOpen): the request does not carry `END`, and the
  client goes on sending in the stream — answers, permits, acknowledgements.

A client's `END` says it has nothing more to send *in* the stream.
[Window](#window) and [Cancel](#cancel) are *about* the stream, and may follow
it until the server ends the stream; arriving after that, they are ignored.

[Cancel](#cancel) ends a stream early. It carries `END`. The server stops
working on the stream, sends nothing more of what it had queued for it, and
answers with RequestFailed with code `cancelled` — unless the stream already
ended, in which case the Cancel is ignored.

### Contexts

Event store requests name their context by a `u16` the connection binds with
[BindContext](#bindcontext), a unary request answered by
[ContextBound](#contextbound). Id 0 is bound to `default` from the start.
Binding checks that the context exists and that the principal may use it, so
requests carry two bytes instead of a name, and a request naming an unbound
id fails with `invalid_argument`. Messaging buses are bound the same way with
[BindBus](#bindbus).

### Flow control

Every stream has a **window**: how many bytes of frames the server may send on
it ahead of the client. Hello's `window` sets it for every stream of the
connection, at least 64 KiB. The server counts each frame it sends on a
stream, header included, against the stream's window, and sends while the
window is positive: one frame may take it below zero, and the next waits. The
frame that ends a stream counts for nothing and never waits, so a stream can
always be ended. As the client's consumer reads a stream's frames, the client
grants their bytes back with [Window](#window). Granting once half the window
has been read keeps the server sending without a pause.

A consumer that falls behind therefore holds back its own stream and nothing
else: the server stays at most a window ahead of it, and waits. No stream is
failed for being read slowly, and the connection's other streams go on. The
client reads every frame as it arrives and keeps it for its stream's
consumer; what it keeps for one stream is bounded by the window. A window
should be at least twice what the link carries in a round trip: the reference
clients grant 8 MiB, and nodes grant each other more, since replication paces
itself with its own acknowledgements.

What a client sends needs no window. Requests are answered one by one, a
handler's answers are bounded by the permits it granted, and a server that is
behind on writing a connection stops reading it, except for the frames that
relieve it: Window, Cancel and ClientPong.

Messages an application counts take **permits**, not bytes:
[Permits](#permits) grants a handler stream more commands or queries, and a
subscription query more updates. Permits say how much work a consumer takes
on; the window says how much it buffers. A stream can have both.

Events frames carry at most a request's `batch_size` events, and never more
than 1 MiB of them.

A subscriber whose criteria rarely match still advances: with a non-zero
`progress_interval`, the server sends [Progress](#progress) while nothing
matches, carrying the position everything before which has been delivered. A
processor can store that position as its token.

## Messaging

Commands, queries and subscription queries travel on buses, named by a `u16`
the connection binds with [BindBus](#bindbus), like contexts. Id 0 is
`default`.

**Dispatching.** [DispatchCommand](#dispatchcommand) is unary and answered by
[CommandResponse](#commandresponse): whatever the handler answered, including
its own failure in `error_code`. Two codes are the server's: `KRONOSDB-4005`
(no answer in time) and `KRONOSDB-4006` (the handler's connection was lost).
A RequestFailed means the command reached no handler: `unavailable` when none
is registered or none has a permit within the timeout. Commands with the same
`routing_key` instruction go to the same handler. [DispatchQuery](#dispatchquery)
is answered by [QueryResponse](#queryresponse) frames, one per result, and
ends with [QueryEnd](#queryend) once every handler is done or the timeout
passes; a `nr_of_results` instruction of 1 asks a single handler. Cancelling
the stream tells the handlers still working on the query
([CancelQuery](#cancelquery)). [OpenSubscriptionQuery](#opensubscriptionquery)
streams [SubscriptionQueryEvent](#subscriptionqueryevent) frames: the initial
result first, then updates, then a completion with END; the subscriber grants
more updates with Permits and ends it with Cancel. An update beyond the
subscriber's permits is dropped, so a handler that must not lose any holds
them until it is told of more.

**Handlers.** [OpenCommandHandlers](#opencommandhandlers) and
[OpenQueryHandlers](#openqueryhandlers) open a stream that lives as long as
the handler. The client subscribes to names (the server answers with
[ServerAck](#serverack) when the instruction id is not empty) and grants
[Permits](#permits); the server sends one command or query per
permit. Permits belong to the stream, not to a name: Permits of 100 means
100 more commands (or queries) of whatever names the stream handles, so a
handler grants its capacity once, typically right after opening the stream,
and tops it up as it answers. Subscribing or unsubscribing a name leaves the
stream's permits as they are. The server also tells a query handler when a subscriber grants
update permits ([SubscriptionQueryPermits](#subscriptionquerypermits)) or
leaves ([CancelSubscriptionQuery](#cancelsubscriptionquery)). A handler
answers a subscription query with [SubscriptionQueryHandled](#subscriptionqueryhandled)
frames: an `initial_result`, `update`s, and `complete` or
`complete_exceptionally`.

Closing the stream, or the connection, unregisters everything it subscribed
and fails the commands in flight to it with `KRONOSDB-4006`. A newer handler
stream of the same client on the same bus replaces an older one, which ends
with `unavailable`.

**Platform.** [OpenPlatform](#openplatform) is a client's long-lived stream.
The server opens it with [NodeInfo](#nodeinfo), sends
[ServerHeartbeat](#serverheartbeat) regularly, which the client answers with
[PlatformHeartbeat](#platformheartbeat). Any frame on the stream counts as a
sign of life; a client silent for the server's heartbeat timeout is removed.
When a client's platform stream ends, for whatever reason, its handler streams
on that server end too, with `unavailable`: handlers belong to the client id
that opened them, and a client is only present while its platform stream is. The client reports its event processors
with [ProcessorStatus](#processorstatus) and answers
[ProcessorInstruction](#processorinstruction) with
[InstructionResult](#instructionresult). [TopologyChange](#topologychange)
announces handler registrations; [RequestReconnect](#requestreconnect) asks
the client to move when the server is shutting down.

**Between nodes.** A node forwards what it routed to another with
[ForwardCommand](#forwardcommand), [ForwardQuery](#forwardquery) and
[RelaySubscription](#relaysubscription), which only a principal with the
`peer` role may send. They are answered exactly like the client requests they
stand for; a relayed subscription takes its update permits and its cancel from
the opening node.

## Errors

A request that fails gets [RequestFailed](#requestfailed) on its stream with
an [ErrorCode](#errorcode) and a message that says what happened and, where
there is something to do, what to do. Codes the client does not know must be
treated as `internal`.

A consistency-condition conflict is not an error: an Append answers
[AppendConflict](#appendconflict).

Bytes that violate this protocol — a truncated or overlong frame, an unknown
or wrong-direction kind on a stream, an invalid UTF-8 string, a bool or option
byte other than 0 or 1 — are answered with RequestFailed on stream 0 with code
`protocol_violation`, and the connection closes.

## Event records

Events travel in the server's on-disk record layout:

```
len u32 | flags u8 | body
```

`len` counts `flags` and the body, `flags` is 0 for an event, and the body is
an [EventRecord](#eventrecord). On disk the same bytes are preceded by a
CRC32C of `flags` and the body, so a stored record goes on the wire as the
slice that starts four bytes in: the server reads events by copying records
from the segment into the frame, with nothing decoded or re-encoded.

The CRC stays on the server. It verifies it on every read, so a corrupted
record is reported as `corrupted` instead of being sent, and computes it on
every append. Between the server and the client, TCP and TLS already guard
the bytes, so the CRC would cost four bytes per event and buy nothing. Peers
replicating a log do receive it: followers write segments byte for byte.

Appends work the same way in reverse: the client sends records with
`position` 0, and the server validates them, sets the position and the CRC,
and writes them.

Records cannot gain fields in a minor version: their layout is the storage
format. Welcome's `record_format` says which layout the connection carries.

## Versioning

Hello carries the highest version the client speaks; Welcome answers with the
version both will use. A server supports the current version and the one
before it — except version 1, which KronosDB 0.11 spoke: its streams had no
windows, and a server refuses it with `rejected`.

Within a version, a frame may gain fields at its end. A decoder therefore
ignores bytes after the fields it knows in a frame body — and only there:
structures inside a frame and record bodies cannot grow. Feature bits, which
Hello requests and Welcome grants, switch on behaviour that changes the
meaning of existing fields. Anything else is a new version.

## Limits

Strings and byte fields declared `str16`/`bytes16` hold at most 65,535 bytes;
`str32`/`bytes32` at most 4 GiB, bounded in practice by `max_frame`. An
encoder fails rather than truncate.

#### EventRecord

The body of a stored event record. This is the on-disk layout, byte for
byte: reads copy records straight from the segment, and appends are
written to disk as sent once the server has validated them and set the
position. Clients send `position` as 0.

A record on the wire is `len u32 | flags u8 | body`, where `len` counts
`flags` plus the body and `flags` is 0 for an event. On disk the record
is preceded by its CRC32C; the server verifies it on every read and
computes it on every append, and it does not travel to clients.
